# CLAUDE.md

Django 6 app (Google login via allauth, gated by the `AllowedUser` table) that plans weeknight dinners. See README.md for the user-facing flow and setup.

## Layout

- `meals/services.py` — the only entry point for plan changes: `generate_week`, `add_meal` / `move_meal` / `remove_meal`, `replace_with_suggestion` / `replace_with_recipe`, `grocery_list`, `push_to_cart`, `send_plan_email`. Views, the `generate_meal_plan` command and `/internal/generate-week/` (which Airflow's `meal_plan_weekly` DAG calls) all go through it.
- `meals/planner.py` — the Claude call. It uses `beta.messages.parse` with Pydantic output models (`WeekChoices`), effort `medium`, and server-side refusal fallbacks. The household context (scored recipes, rating comments, the last 6 weeks of meals, swap reasons, archived recipes) is built in `_household_context`.
- `meals/calendar_sync.py` — Google Calendar through a service account. Failures are logged, not raised, so a calendar outage never loses a plan. The event time is set only on insert; later syncs `events.patch` just the title, description and link, so times (and guests, reminders, colours) people change in Google Calendar are never overwritten. The one exception is `move_meal_event`, used when a meal changes day: it shifts the event by whole days, keeping the event's current local time and length.
- `meals/kroger.py` — Kroger API: user OAuth tokens are kept in the `KrogerAuth` singleton, product and location search use a client-credentials token, and `PUT /cart/add` fills the cart. Remembered UPCs live in `GroceryProduct`.
- `meals/photos.py` — recipe photos. After `generate_week` / `add_meal` / `replace_with_suggestion` commit, `fetch_missing_photos_soon` searches Pixabay (food photos; downloaded, as Pixabay forbids lasting hotlinks) on a background thread (by the planner's `NewRecipe.photo_query`, then the short name), so planning never waits on it; each recipe is searched once (`photo_searched_at`, claimed atomically; un-claimed on network errors). Anyone can upload their own (re-encoded to a ≤1600px JPEG, EXIF stripped), which wins over the stock photo. Bytes live in `RecipePhoto` in the database, not on disk (the container filesystem is wiped on redeploy); `Recipe.photo_*` holds the credit and `photo_url` (versioned for caching), so list pages never load the bytes.
- UI: server-rendered Bootstrap 5 templates styled by `static/global/css/global.css` ("Cast Iron" tokens, `--mp-*`, mirroring Simpli Budget's mobile-first shell: phone tab bar, bottom sheets, mono titles). Dark is the default; the `theme` cookie (set by `static/global/js/global.js`) picks light, read by `meals.context_processors.ui`, which also sets `nav_section`. Use the tokens, not hard-coded colours.
- Preferences: `/preferences/` sets the household's meal schedule (`meal_schedule`: which weekdays get a breakfast, lunch and/or dinner, with `MEAL_SCHEDULE_PRESETS` quick picks), cooking time (`max_weeknight_minutes`, one of `COOK_TIMES`), `protein_preferences`, `favorite_cuisines`, `meal_styles` and `dietary_notes` on `HouseholdSettings`, plus each member's own loves/dislikes in `MemberPreferences`. Option lists live in `models.py`; `planner._preferences` turns them into the `preferences` block of the household context, and `SYSTEM_PROMPT` says how strictly to apply each.
- `HouseholdSettings` (pk=1) and `KrogerAuth` (pk=1) are singletons. `/settings/` (any member) connects King Soopers and picks the store (`kroger_location_id` / `_name`, via `kroger.find_locations`), and sets `calendar_id` (checked with `calendar_sync.check_access` before saving, then this week is synced); everything else in `HouseholdSettings` is edited in /admin/. Until preferences, Kroger, the store, a calendar and a first plan exist, the week page shows a setup checklist (`views._setup_steps`).

## Conventions

- Weeks run Sunday through Saturday (`week_start_for`). Plans are unique per `week_start`, and meals are unique per (plan, date, `meal_type`); `services.plan_slots` turns the schedule, adjusted by that week's `MealPlan.slot_overrides`, into (date, meal_type) pairs, which is what `planner.choose_week` fills. `services.add_meal` / `move_meal` / `remove_meal` change one week only: they record an override (true = added, false = removed) so regenerating or re-running the weekly job keeps the change. Moving onto a day that already has that meal type trades the two rows' contents (recipe, why, lock, event id) rather than their dates, so the unique constraint is never violated. Each meal type has its own event time (`HouseholdSettings.meal_window`).
- `generate_week` is idempotent: it only fills empty slots, unless `regenerate=True`, which re-picks unlocked meals.
- While Claude is planning, `generate_week` holds `MealPlan.generating_since` (claimed atomically, cleared in `finally`, ignored after `GENERATING_STALE_AFTER` in case the worker was killed). A second run for that week raises `PlanBusy`; the week page shows a "Planning this week…" banner and polls `/plan/<week>/status/` until it can reload.
- Tests (`SECRET_KEY=dev python manage.py test meals`) run on SQLite with Claude/Calendar/Kroger mocked. `PlannerRequestTests` goes through the real SDK request/parse path using an httpx2 MockTransport.
- Production must run on Postgres (`DB_HOST` set). With `DEBUG` off and no `DB_HOST`, settings raise `ImproperlyConfigured` rather than fall back to SQLite, because a SQLite file inside the container is wiped on every redeploy (that wiped `AllowedUser` and every plan twice). Tests and `DEBUG=1` still use SQLite.
- Never commit `.env*` or `secrets/`.
